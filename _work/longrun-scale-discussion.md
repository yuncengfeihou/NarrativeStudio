## 0. 一句话结论（先读这段）

**你担心的「几百个伏笔/NPC/时间地点全塞进上下文」不会发生——不是因为系统会优雅地压缩，
而是因为它们会在 45–110 拍之间依次撞上四道「读取条数硬顶」，然后静默消失。**

所以真正的问题不是「塞不下」，是**塞不下的时候没有任何信号**：库里还有 6000 条断言，
模型只看到最近 48 拍的 300 条，而它不知道更早的还在。这正是「自造 canon」「布包被首次发现
三次」这类现象的温床——模型忘了，于是重新发明了一遍。

| 结论 | 依据 |
|---|---|
| 上下文**总量**不是瓶颈 | 45 拍峰值 21316 tok，soft 配额 102300，硬上限 186000 |
| 场次索引**设计良好** | token 配额驱动 + 显式降级 + 从最旧端降，meta 记录丢了什么 |
| 断言/线索/关系/原声**有四道静默硬顶** | 300 / 40 / 60 / 400 行，全部是 SQL `LIMIT`，不参与 token 预算 |
| 「加预算」救不了后四者 | 它们是条数驱动，调 `softMax` 一点用都没有 |
| 默认模式下模型**无法回查历史原文** | `recall_history` 只在分段模式存在，默认 single 没有任何 tools |

## 1. 容量天花板实测（所有讨论的基线）

### 1.1 各记忆载体：每拍新增 vs 装配时读取上限

| 载体 | 每拍新增（实测） | 装配时读取上限 | **有效覆盖** | 到顶时的行为 |
|---|---|---|---|---|
| `scenes` 场次索引 | 0.45 场/拍（2.24 拍/场） | token 配额 30690，**无行数上限** | **~400 场无损、~987 场硬顶** | 最旧端 major→normal→minor 降级，再整行丢；meta 记 `dropped/degraded` |
| 逐字原文 `recent` | 2 行/拍 | **无 token 上限，从不裁** | 当前场次（封场前全部） | 封场即整体消失，只剩索引一行 |
| `assertions` 断言 | ~6.2/拍 | `LIMIT 300`，`valid_from DESC` | **约最新 48 拍** | 静默丢更早；meta 有 `many_dropped` 但无消费方 |
| `threads` 线索 | ~0.9/拍 | `LIMIT 40` | **40 条**（按 status+weight 排，不按新旧） | 静默丢 |
| `relations` 关系 | ~0.8/拍 | `LIMIT 60` | **60 条**（按 \|sentiment\| 排） | 静默丢 |
| `voices` 原声 | ~3.6/拍 | `getVoiceMap` 读 400 行 + `perWho 3` | 最新 400 行 / 每人 3 句 | 静默丢 |
| `patches` 幕外流言 | ~1/切场 | `LIMIT 24`（按 kind 过滤） | 最近 24 条 | 静默丢 |
| `world_state` 增量 | ~15/拍 | **无 limit，全量回放** | 全量 | 无上限，回放耗时线性涨（1100 行 ≈ 10.7ms/次投影） |
| 世界索引 `entities` | ~1 `introduce`/拍 | token 配额 30088 | 310（卡内）+ 估 ~1200 | 降级成名字清单→截断；`meta.index.dropped_names` |

**四道静默硬顶的撞墙点**（按实测速率外推）：

```
第 ~48 拍   assertions 撞 300 条     ← 45 拍长跑刚好没撞到
第 ~43 拍   threads    撞 40 条      ← 长跑末态 60 条/55 open，已经撞了
第 ~73 拍   relations  撞 60 条      ← 长跑末态 53，差一点
第 ~111 拍  voices     撞 400 行     ← 长跑末态 234，没撞
第 ~515 拍  场次索引开始降级（59.6 tok/轮 × 515 ≈ 30690）
第 ~987 场  场次索引开始整行丢弃
```

### 1.2 场次索引的真实容量（合成样本，密度按长跑实测 112.6 tok/场校准）

```
importance 分级（major:normal:minor = 1:1:1）
  400 场   30674 tok   无损      ← 开始降级
  532 场   30664 tok   degraded 253/532
  700 场   30652 tok   degraded 524/700
  987 场   30698 tok   硬顶（rendered 987, dropped 13）
  2000 场  30698 tok   rendered 987, dropped 1013
```

按 2.24 拍/场换算：**约 894 拍无损、2200 拍硬顶**。这个设计是对的——它有配额、有降级顺序、
有 meta 记账，符合 AGENTS §6.3。

### 1.3 世界索引的真实容量

```
当前卡 310 实体 → 4529 tok（system 配额 32736，占 13.5%）
每个实体 ≈ 21.5 tok
+50 实体 → +1076 tok；+700 实体 → 19598 tok
配额 30088 可装约 1500 个实体
```

**但有个结构性问题（本段新发现，实测确认）**：`buildSystemLayer()` 的索引读的是
**`templateCard`（冻结快照）**，不是 `buildEffectiveWorld()` 的投影结果
（`server/memory/context-engine.js:830-836`）。所以：

- 剧情里 `introduce` 出来的新人物/新地点，**永远不会出现在世界索引里**；
- 它们只有在史官同时写了账本 `present` 或断言之后，才能进场记单；
- 实测：只 `introduce` 一个「卖炭翁张三」→ 上下文全文 0 次出现；补一条 `present` → 出现；
  补一条断言 → 以「事实」形态出现。

这条**不是 bug**（AGENTS §6.2「system 必须逐字节冻结」就是这么设计的，实测 6 拍连续
`system` 逐字节一致），但它的代价此前没有被量化：**新造实体只能靠场记单那几行活着**——
`role` 会渲染（括号里）、`status`/`psyche.traits` 会渲染，但 `summary` 不渲染，
`identity`/`voice` 连库都进不去（见 D8 实测）。所以一个新人物在 introduce 之后，
模型能记住的就是「名字 + 职业 + 一条状态 + 几个性格词」，其余全是断言里的一句话。

## 2. 你提的两条观点，核实结果

### 2.1 「预算配额压得太死，200K 压到 100K 多点，可以提高预算丰富记忆内容」

**核实结论：成因对，但结论不成立——现在的约束不是预算。**

- 成因确实是 `AUTO_SOFT_RATIO = 0.55`（`server/memory/context-plan.js:54`）：
  `softMax = hardMax × 0.55 = 186000 × 0.55 = 102300`。
- 但 45 拍真实长跑的峰值只有 **21316 tok**，是 softMax 的 **20.8%**。
  也就是说**降级路径一次都没触发过**（`degraded=[]` 全程）。
- 提预算只会让「场次索引」和「世界索引」两层能装更多（它们是 token 配额驱动的）；
  对断言/线索/关系/原声**完全无效**——那四层是 SQL `LIMIT` 驱动的，300 条就是 300 条。

→ 所以「加预算」和「几百轮记忆」是两件不同的事。前者在 45 拍这个长度上**完全不是瓶颈**
（想改也是一个数字的事：`CONTEXT_SOFT_TOKENS=140000`，或把 `AUTO_SOFT_RATIO` 提到 0.7–0.75）。

**顺带算清了一笔账**（之前没写死过）：`recent` 的 0.40 份额**与另外六层不重叠**，
所以「softMax + recent」= 102300 + 40920 = **143220 tok**，而 `hardMax` 是 **186000 tok**。
也就是说**软目标全部打满，离硬上限还有 42.8K 的余量**。
现在真实峰值 21316 tok，连「softMax + recent」的 15% 都不到。
预算确实宽裕——所以 §1.1 那四道 SQL 硬顶才显得刺眼：**钱没花完，东西已经不给了**。

**但有一个真实的理由支持加预算**：场次索引在 515 拍开始降级。如果目标是「千拍不降级」，
`softMax` 需要 ×2（archive 从 30690 到 ~61000）。这是个明确的取舍，见 D2。

### 2.2 「应该保留上一轮甚至前两轮原文，让对话衔接更自然连续，而不是靠简要记忆总结」

**核实结论：在当前场次内，这个要求本来就是满足的；问题出在「封场」这个动作上。**

- `recent` 层的窗口是「`turn_no > sceneCoveredTo` 的全部回合」
  （`server/memory/context-engine.js:849-858`），**不是「最后 N 轮」，也不做 token 裁剪**。
  所以只要没封场，上一轮、上上轮原文都在。
- **一旦封场，整场逐字原文全部消失**，只剩场次索引里的一行 + 场次细节块里的一段
  `renderRecentScenes`（最近 1–2 场的 outcome/细节/因果/钩子）。
- 长跑实测 `recent_from=null` 占 **44.6%**（`MIN_SCENE_TURNS` 修好之前）。
  这直接解释了引号风格的逐拍随机（`「」`17 / `“”`13 / ASCII 1，13 次切换里 9 次发生在
  recent 为空时）——模型看不到上一段正文用什么引号，只能自己重新选一次。

→ 这条你的直觉是**对的**，而且它指向一个很便宜的修复：见 D1。

### D1【低成本高收益】封场后保留最近 1–2 拍原文尾巴

**先解释这条在说什么（第 2 问）**

现在的上下文里，「最近的正文」是按**场次**切的，不是按轮数切的：

```
场景一：正在演的这一场还没结束
  【本场原文】第 11 拍 PC / 第 12 拍 旁白 / 第 13 拍 PC / …（这一场从头到现在的全部原文，一句不少）

场景二：刚刚切了场（比如玩家从「回春堂」走到「雨街」）
  【场次索引】第 1 场 ……（一行）
  【场次细节】上一场结局是……
  【本场原文】第 14 拍 PC（只有这一条，因为新场次刚开头）
     ↑ 第 11–13 拍的原文，全部消失了
```

「重叠 2 拍」的意思就是：**切场之后，不要把那 2 拍原文删掉，让它们同时出现在
「场次索引」和「本场原文」里**。代价是多花 2 拍的 token（同一段文字出现两次），
好处是模型在新场次开头还能看到「上一场最后一句话是怎么说的」。

为什么这重要：**逐字特征（引号用「」还是“”、她管他叫「你」还是「卿儿」、句子长短节奏）
是摘要传不过去的**。长跑里引号风格 13 次切换，9 次正好发生在「刚切场、原文为空」的时候。

- **问题**：封场瞬间，上一段正文从上下文里彻底消失，衔接靠一段 summarise 过的「场次细节」。
- **证据**：`recent_from=null` 44.6%；引号风格切换 9/13 发生在该状态。
- **方案**：
  - **A. 让 `recent` 下界取 `max(scene_to+1, turnNo-2)`**——即允许原文窗口与场次
    **重叠**最近 2 拍。成本：约 2 × 1164 tok ≈ 2330 tok（重复 token，不是新信息）。
    代价：违反现行「场次与原文不重叠」的表述（AGENTS §13.14），但那条的实质是
    「不能有洞」「不能在场次接住之前丢掉中间剧情」，重叠不在其禁令范围内——
    需要明确改写那句话。
  - **B. 加大 `archiveDetail`（现 6138 tok）并让 `renderRecentScenes` 保留更多场次**——
    仍然是摘要，救不了「引号/称谓/语气」这类逐字特征。
  - **C. 不做**，靠 `MIN_SCENE_TURNS=2` 把场次拉长来降低封场频率（已落地）。
- **我的倾向**：**A**。它是唯一能保住「逐字特征」的方案，成本 2–3K tok（占 soft 的 2%）。
- **已定（你 m06330）**：**重叠 2 拍，且「一拍」必须是 agent 的一拍**。
  这条提醒很关键，实现上有陷阱：`turns` 表里**一拍 = 两条行**
  （一条 `kind='player'` + 一条 `kind='narrator'`，共用同一个 `turn_no`）。
  如果按「最后 2 条消息」实现，拿到的会是「1 条 player + 1 条 narrator」= **只有 1 个 agent 回合**。
  正确的写法是锚定 `turn_no`：`from = max(sceneCoveredTo + 1, turnNo - 2)`，
  `turnNo` 是本轮编号，减 2 得到「上两拍」的编号——每个编号自然带出它自己的
  player + narrator 两条行。这样才是「agent 的两拍」。
  实现改 `server/memory/context-engine.js:849-851`，并在 `coverage` 里加
  `overlap_turns` 记账（现有 `recent_from` 会因此变小，测试里要同步）。

### D4【必须做，且你的方案更好】让便宜 agent 去查历史，而不是让旁白自己查

- **问题**：`recall_history` 与 `codex_lookup` 两个「模型主动取证」通道**只存在于分段模式**
  （`server/agents/orchestrator.js:200-211` 只在 `narrationMode === 'segmented'` 注入
  `recall` 回调；`server/agents/narrator.js` 完全没有任何 tools）。
  默认 `NARRATION_MODE=single`，所以 45 拍长跑里模型**没有任何手段回查**。
- **证据**：这是「布包被首次发现三次，三版互斥」「P1/P3/P4 三条语境级探针全编造」的
  结构性解释——不是模型不努力，是通道不存在。
- **你说的「用另一个快的 agent 来做」是对的，而且代码里已经有 80% 的现成东西**：
  `runRetrieval()`（`server/agents/retrieval.js`）就是一个**独立的、可单独绑便宜模型的
  资料员 agent**——它已经做到了这件事，只不过查的是**辞书**（设定全文），不是**历史原文**。
  实测成本（45 拍长跑）：19 次调用、共 30790 prompt + 11135 completion
  ≈ **每次 1.6k prompt / 586 completion**，是全场最便宜的 agent（旁白是 682k prompt）。
- **方案（按你的思路重写）**：
  - **A. 把「回查历史」并进同一个资料员调用（推荐）**：现在的资料员已经每拍判断
    「要不要查辞书全文」，加问一句「要不要回查历史原文、查什么」，由代码执行
    `recallHistory()`，结果同样进 `retrieval` 层、**当拍蒸发**。
    **零额外往返**（piggyback 在同一次调用里），延迟 +0，成本 +~200 tok/拍。
    它与 `codex_lookup` 完全同构：预检只决定「要不要查」，不决定注入哪段内容——
    红线 1 允许的唯一例外就是这个形态。
  - **B. 让旁白自己发一次工具调用**（我原来的方案）：每拍多一次**全量上下文的
    narrator 往返**（+15–25% 延迟、+30% 成本）。**现在看不如 A**：

### D5【已按你的意思改判】线索的问题不是「不收」，是「埋太多」

- **你的回答（逐字要点）**：「肯定能收就收，但关键在于哪有那么多线索，
  十几个甚至几十个线索让 agent 一个个回收怎么可能完成。要管住的是线索的**数量**，
  解决完几个再来埋几个，而不是越堆越多。」
- **你指出的才是根因，我原来的方案（提高回收率）只是治症状**：
  - 现状：65 拍 **埋 37 条、收 4 条**（10.8%），末态 open 55 条。
  - 但即使回收率提到 100%，按 0.9 条/拍的埋设速度，50 拍也会堆到 45 条——
    **因为根本没有上限**。
  - 而且渲染端只显示 `slice(0, 8)`（`server/world/scene-sheet.js:515`），
    所以超过 8 条之后，**埋得越多、每条越看不见**——这是最坏的结果：花了 token 记账，
    模型却看不到。
- **方案**：
  - **A. 加 open 线索 WIP 上限（推荐）**：`config` 加 `THREAD_WIP_LIMIT`（建议 6，
    与渲染端 `slice(0,8)` 留余量）。**到顶时 `plant` 被代码拒绝**（记一条
    `patch(kind='thread_rejected')`，不静默丢）。效果：从「无限堆」变成「必须先收再埋」。
    同时提示词里给出「当前已开放 N 条，上限 6」这个事实（不是催告，是让模型知道约束），
    并允许 `resolve` 时按标题模糊匹配（现在要求标题**完全一致**才收得掉，
    这是回收率低的直接技术原因，见 `archivist.js:816`）。
  - **B. 只降浇埋设速率**（提示词里说「一场最多埋一条」）：不改代码，但靠提示词约束，
    实测这类"别做太多"的指令在长跑里会被稀释。
  - **C. A + B 一起**（推荐组合）：代码兜住硬上限（不可绕过），提示词解释为什么
    （模型知道上限就不会反复试）。
- **我的倾向**：**C**，上限取 **6**。理由：6 条正好是「一张网能同时张开的伏笔数」，
  也匹配渲染端 8 条的容量；50 拍里 6 open + 若干 resolved 总计十几条，
  与你说的「很多玄幻小说都没这么多线索」一致。
  - **顺带两个真要修的技术细节**（回收率 10.8% 的直接原因，都是确定性的）：
    ①`resolve` 要求 `title` 与库里的**完全一致**（`archivist.js:816` 的
    `open.find((x) => x.title === title)`），模型记不住原话就永远收不掉；
    ②传给史官的「未回收线索」清单只有 **12 条**（`archivist.js:536` 的
    `getThreads(..., limit: 12)`），而 open 有 55 条——**第 13 条起连被回收的机会都没有**。
    这两条不改，加多少提示词都没用。
- **待拍板（已被你 m06330 回答，下面是落实方案）**：
- **已定（你 m06330）**：**主战场是提示词，WIP 上限只作保底**；并且要加一层**分级判断**——
  「没什么意思、作用不大的细节没必要当成伏笔」。
  → 这改变了实现重点：不是「先加上限再补提示词」，而是**先把「什么才算线索」讲清楚**，
  上限只兜住模型仍要多埋的情况。
  1. **改判据（主手段）**：`server/prompts/archivist.js:136-139` 现在只有一句否定式
     「不要为凑数而编造线索；只有正文真的留下了『未解之事』才记」——模型只能自己猜
     什么叫未解之事。改成**正反两面给判据**：
     - 该记：读者会追问「后来呢」的事——谁做了没交代的事、留下了没解释的物件、
       许下没兑现的诺言、被刻意隐瞒的动机。
     - 不该记：气氛、情绪、普通动作、本场已经交代清楚的事。
     - 加一句量级预期：「大多数拍不该产生新线索」。
     §1.2「先删后加」要求这是**替换**原 3 行判据（原段约 120 字），新段控制在同量级。
  2. **用 `weight` 做分级，但给它真语义（你说的分级判断）**：现在 `weight` 只有
     「主线 0.8-1.0 / 小悬念 0.3-0.5」两档，且渲染端只在 `>= 0.8` 打「［主线］」标签
     （`scene-sheet.js:516`）。建议改成 **`weight < 0.6` 不落 `threads`**——
     「没什么意思的细节」在输入端就被挡掉，而不是等它堆起来再清理。
  3. **代码保底（你说的上限）**：`config` 加 `THREAD_WIP_LIMIT = 6`；到顶时 `plant`
     被拒并记 `patch(kind='thread_rejected')`。**这不是主要手段**，是防模型硬顶约束。
  4. **两处确定性 bug 一起修**（回收率 10.8% 的直接原因，与提示词无关）：
     ①`resolve` 的 title 完全匹配改**归一化匹配**（去标点/空白后互含即算命中，
     现 `archivist.js:816` 是 `x.title === title`）；
     ②传给史官的未回收清单从 12 条改成**全部 open**（现 `archivist.js:536` `limit: 12`；
     open 55 条时第 13 条起连被回收的机会都没有）。有了 WIP 上限 6 之后这一步反而更便宜
     （清单最多 6 行）。
- **我建议的上限**：**6**。理由：6 条是「一张网能同时张开的伏笔数」，
  也匹配渲染端 8 条的容量；与你说的「很多玄幻小说都没这么多线索」一致。
- **上限到顶的行为**：**拒绝新埋**（不搞 dormant 转换）。理由：dormant 需要定义
  「谁该休眠」，当归一化/权重规则一变就会产生新的静默；拒绝 + 留痕更简单，
  而且提示词既然已经教了判据，被拒本身就是个信号。

### D6【先解释，再拍板】`uncertain` 是什么、要不要留

**先解释这是什么（第 5 问）**

史官（负责记事的 agent）每拍读完正文后，除了记「发生了什么」，还会记一份
「**正文没写清楚、我不敢当事实记下来**」的清单。这一份就叫 `uncertain`。

它的提示词原话是（`server/prompts/archivist.js:3`）：

> 「宁可少记，绝不编造。正文没有明说的，**一律放到 uncertain，不许当成事实**。」

举例：正文写「她把银子推回去，没说具体多少」。史官就把
「`银子具体数额`」放进 `uncertain`，而不是自己猜一个数字记进账本。

- **它现在的作用**：一个「防止史官编造」的减压阀——不给它这个出口，
  它可能会把猜的东西直接当事实写。
- **它现在的去向**：写进 `patches` 表，标 `status='open'`，**然后没有任何 agent 读它**。
  45 拍长跑里积了 209 条（每拍 2–5 条、去重率 0.5%），已加 `retirePatchesBeyond(keep:120)`
  限制增长。记忆面板里会显示，但基本上没人看。
- **所以这是一个「只进不出」的抽屉**：留着当纪律有用，当数据没用。

- **方案**：
  - **A. 保留提示词的出口，但不再落库**（推荐）：模型照样可以说「这个我没把握」，
    但只体现在它**不写**这条记录上，不再往 `patches` 表塞一行。
    效果：减压阀保留（防止编造），抽屉清空（209 行噪音消失）。
    成本：删一个循环（`archivist.js:907-920`）。
  - **B. 交给校勘读**：校勘本来就在找矛盾，「史官说这里没写清」确实是它的输入。
    但代价是校勘提示词要多一段（违反 §1.2 先删后加），且校勘只每 12 拍跑一次，
    拿到的是一堆分散的短句，能做的事有限。
  - **C. 什么都不改**。它已经被 `keep:120` 兜住了，代价只是表里多 120 行。
- **我的倾向**：**A**。理由符合 §1.2「先删后加」：没有消费方的落库就是纯成本；
  但**提示词那一条要留着**——它不是给数据用的，是给模型用的减压阀，删了可能诱发编造。
  （B 听起来聪明，但把「史官的自述清单」喂给校勘，本质上还是让它去猜，
  而它猜的依据已经在场次原文里了。）
- **已定（你 m06330）**：**保留出口，不再落库**。
  即：`server/prompts/archivist.js:3` 那句「正文没有明说的，一律放到 uncertain，
  不许当成事实」**原文保留**（这是给模型的台阶，防止它硬编），
  但 `server/agents/archivist.js:904-920` 那段写 `patches` 的循环**整段删掉**。
- **需要一起处理的两处**（否则留下悬空引用）：
  ①`archivist.js:456` 的解析仍保留 `uncertain` 字段（模型输出里还有它，不解析会报错/
  落进未知字段）——保留解析，只是不落库；
  ②`retirePatchesBeyond({ kind: 'uncertain' })` 这个调用只服务这一处，一并删；
  ③`store.js` 里为 `uncertain` 写的注释（`:1597`、`:1627`、`:1644`）要改，
  否则以后没人知道为什么留了个 kind 却没有写入方。
- **验证方式**：跑一局 8 拍，确认 `patches` 表里 `kind='uncertain'` 计数为 0
  （历史数据里已有的保留，不删）。
