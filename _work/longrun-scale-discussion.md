## 0. 一句话结论（先读这段）

**你担心的「几百个伏笔/NPC/时间地点全塞进上下文」不会发生——不是因为系统会优雅地压缩，
而是因为它们会在 45–110 拍之间依次撞上四道「读取条数硬顶」，然后静默消失。**

所以真正的问题不是「塞不下」，是**塞不下的时候没有任何信号**：库里还有 6000 条断言，
模型只看到最近 48 拍的 300 条，而它不知道更早的还在。这正是「自造 canon」「布包被首次发现
三次」这类现象的温床——模型忘了，于是重新发明了一遍。

| 结论 | 依据 |
|---|---|
| 上下文**总量**不是瓶颈 | 45 拍峰值 21316 tok，soft 配额 102300，硬上限 186000 |
| 场次索引**设计良好** | token 配额驱动 + 显式降级 + 从最旧端降，meta 记录丢了什么 |
| 断言/线索/关系/原声**有四道静默硬顶** | 300 / 40 / 60 / 400 行，全部是 SQL `LIMIT`，不参与 token 预算 |
| 「加预算」救不了后四者 | 它们是条数驱动，调 `softMax` 一点用都没有 |
| 默认模式下模型**无法回查历史原文** | `recall_history` 只在分段模式存在，默认 single 没有任何 tools |

## 1. 容量天花板实测（所有讨论的基线）

### 1.1 各记忆载体：每拍新增 vs 装配时读取上限

| 载体 | 每拍新增（实测） | 装配时读取上限 | **有效覆盖** | 到顶时的行为 |
|---|---|---|---|---|
| `scenes` 场次索引 | 0.45 场/拍（2.24 拍/场） | token 配额 30690，**无行数上限** | **~400 场无损、~987 场硬顶** | 最旧端 major→normal→minor 降级，再整行丢；meta 记 `dropped/degraded` |
| 逐字原文 `recent` | 2 行/拍 | **无 token 上限，从不裁** | 当前场次（封场前全部） | 封场即整体消失，只剩索引一行 |
| `assertions` 断言 | ~6.2/拍 | `LIMIT 300`，`valid_from DESC` | **约最新 48 拍** | 静默丢更早；meta 有 `many_dropped` 但无消费方 |
| `threads` 线索 | ~0.9/拍 | `LIMIT 40` | **40 条**（按 status+weight 排，不按新旧） | 静默丢 |
| `relations` 关系 | ~0.8/拍 | `LIMIT 60` | **60 条**（按 \|sentiment\| 排） | 静默丢 |
| `voices` 原声 | ~3.6/拍 | `getVoiceMap` 读 400 行 + `perWho 3` | 最新 400 行 / 每人 3 句 | 静默丢 |
| `patches` 幕外流言 | ~1/切场 | `LIMIT 24`（按 kind 过滤） | 最近 24 条 | 静默丢 |
| `world_state` 增量 | ~15/拍 | **无 limit，全量回放** | 全量 | 无上限，回放耗时线性涨（1100 行 ≈ 10.7ms/次投影） |
| 世界索引 `entities` | ~1 `introduce`/拍 | token 配额 30088 | 310（卡内）+ 估 ~1200 | 降级成名字清单→截断；`meta.index.dropped_names` |

**四道静默硬顶的撞墙点**（按实测速率外推）：

```
第 ~48 拍   assertions 撞 300 条     ← 45 拍长跑刚好没撞到
第 ~43 拍   threads    撞 40 条      ← 长跑末态 60 条/55 open，已经撞了
第 ~73 拍   relations  撞 60 条      ← 长跑末态 53，差一点
第 ~111 拍  voices     撞 400 行     ← 长跑末态 234，没撞
第 ~515 拍  场次索引开始降级（59.6 tok/轮 × 515 ≈ 30690）
第 ~987 场  场次索引开始整行丢弃
```

### 1.2 场次索引的真实容量（合成样本，密度按长跑实测 112.6 tok/场校准）

```
importance 分级（major:normal:minor = 1:1:1）
  400 场   30674 tok   无损      ← 开始降级
  532 场   30664 tok   degraded 253/532
  700 场   30652 tok   degraded 524/700
  987 场   30698 tok   硬顶（rendered 987, dropped 13）
  2000 场  30698 tok   rendered 987, dropped 1013
```

按 2.24 拍/场换算：**约 894 拍无损、2200 拍硬顶**。这个设计是对的——它有配额、有降级顺序、
有 meta 记账，符合 AGENTS §6.3。

### 1.3 世界索引的真实容量

```
当前卡 310 实体 → 4529 tok（system 配额 32736，占 13.5%）
每个实体 ≈ 21.5 tok
+50 实体 → +1076 tok；+700 实体 → 19598 tok
配额 30088 可装约 1500 个实体
```

**但有个结构性问题（本段新发现，实测确认）**：`buildSystemLayer()` 的索引读的是
**`templateCard`（冻结快照）**，不是 `buildEffectiveWorld()` 的投影结果
（`server/memory/context-engine.js:830-836`）。所以：

- 剧情里 `introduce` 出来的新人物/新地点，**永远不会出现在世界索引里**；
- 它们只有在史官同时写了账本 `present` 或断言之后，才能进场记单；
- 实测：只 `introduce` 一个「卖炭翁张三」→ 上下文全文 0 次出现；补一条 `present` → 出现；
  补一条断言 → 以「事实」形态出现。

这条**不是 bug**（AGENTS §6.2「system 必须逐字节冻结」就是这么设计的，实测 6 拍连续
`system` 逐字节一致），但它的代价此前没有被量化：**新造实体只能靠场记单那几行活着**——
`role` 会渲染（括号里）、`status`/`psyche.traits` 会渲染，但 `summary` 不渲染，
`identity`/`voice` 连库都进不去（见 D8 实测）。所以一个新人物在 introduce 之后，
模型能记住的就是「名字 + 职业 + 一条状态 + 几个性格词」，其余全是断言里的一句话。

## 2. 你提的两条观点，核实结果

### 2.1 「预算配额压得太死，200K 压到 100K 多点，可以提高预算丰富记忆内容」

**核实结论：成因对，但结论不成立——现在的约束不是预算。**

- 成因确实是 `AUTO_SOFT_RATIO = 0.55`（`server/memory/context-plan.js:54`）：
  `softMax = hardMax × 0.55 = 186000 × 0.55 = 102300`。
- 但 45 拍真实长跑的峰值只有 **21316 tok**，是 softMax 的 **20.8%**。
  也就是说**降级路径一次都没触发过**（`degraded=[]` 全程）。
- 提预算只会让「场次索引」和「世界索引」两层能装更多（它们是 token 配额驱动的）；
  对断言/线索/关系/原声**完全无效**——那四层是 SQL `LIMIT` 驱动的，300 条就是 300 条。

→ 所以「加预算」和「几百轮记忆」是两件不同的事。前者在 45 拍这个长度上**完全不是瓶颈**
（想改也是一个数字的事：`CONTEXT_SOFT_TOKENS=140000`，或把 `AUTO_SOFT_RATIO` 提到 0.7–0.75）。

**顺带算清了一笔账**（之前没写死过）：`recent` 的 0.40 份额**与另外六层不重叠**，
所以「softMax + recent」= 102300 + 40920 = **143220 tok**，而 `hardMax` 是 **186000 tok**。
也就是说**软目标全部打满，离硬上限还有 42.8K 的余量**。
现在真实峰值 21316 tok，连「softMax + recent」的 15% 都不到。
预算确实宽裕——所以 §1.1 那四道 SQL 硬顶才显得刺眼：**钱没花完，东西已经不给了**。

**但有一个真实的理由支持加预算**：场次索引在 515 拍开始降级。如果目标是「千拍不降级」，
`softMax` 需要 ×2（archive 从 30690 到 ~61000）。这是个明确的取舍，见 D2。

### 2.2 「应该保留上一轮甚至前两轮原文，让对话衔接更自然连续，而不是靠简要记忆总结」

**核实结论：在当前场次内，这个要求本来就是满足的；问题出在「封场」这个动作上。**

- `recent` 层的窗口是「`turn_no > sceneCoveredTo` 的全部回合」
  （`server/memory/context-engine.js:849-858`），**不是「最后 N 轮」，也不做 token 裁剪**。
  所以只要没封场，上一轮、上上轮原文都在。
- **一旦封场，整场逐字原文全部消失**，只剩场次索引里的一行 + 场次细节块里的一段
  `renderRecentScenes`（最近 1–2 场的 outcome/细节/因果/钩子）。
- 长跑实测 `recent_from=null` 占 **44.6%**（`MIN_SCENE_TURNS` 修好之前）。
  这直接解释了引号风格的逐拍随机（`「」`17 / `“”`13 / ASCII 1，13 次切换里 9 次发生在
  recent 为空时）——模型看不到上一段正文用什么引号，只能自己重新选一次。

→ 这条你的直觉是**对的**，而且它指向一个很便宜的修复：见 D1。

## 3. 决策项清单

每条给：**问题 / 证据 / 方案 / 我的倾向 / 待拍板**。
优先级按「代价 ÷ 收益」排，不按问题严重性排。

---

### D1【低成本高收益】封场后保留最近 1–2 拍原文尾巴

- **问题**：封场瞬间，上一段正文从上下文里彻底消失，衔接靠一段 summarise 过的「场次细节」。
- **证据**：`recent_from=null` 44.6%；引号风格切换 9/13 发生在该状态。
- **方案**：
  - **A. 让 `recent` 下界取 `max(scene_to+1, turnNo-2)`**——即允许原文窗口与场次
    **重叠**最近 2 拍。成本：约 2 × 1164 tok ≈ 2330 tok（重复 token，不是新信息）。
    代价：违反现行「场次与原文不重叠」的表述（AGENTS §13.14），但那条的实质是
    「不能有洞」「不能在场次接住之前丢掉中间剧情」，重叠不在其禁令范围内——
    需要明确改写那句话。
  - **B. 加大 `archiveDetail`（现 6138 tok）并让 `renderRecentScenes` 保留更多场次**——
    仍然是摘要，救不了「引号/称谓/语气」这类逐字特征。
  - **C. 不做**，靠 `MIN_SCENE_TURNS=2` 把场次拉长来降低封场频率（已落地）。
- **我的倾向**：**A**。它是唯一能保住「逐字特征」的方案，成本 2–3K tok（占 soft 的 2%）。
  实现只改 `context-engine.js:849-851` 一行，加一条 `meta.coverage.overlap_turns` 记账。
- **待拍板**：是否同意「原文与场次允许重叠最多 2 拍」这条不变量改写？重叠 1 拍还是 2 拍？

---

### D2【中等成本】场次索引的容量预算：要不要为「千拍」提前留空间

- **问题**：515 拍开始降级（最旧场次先掉细节），987 场开始整行丢。
- **证据**：§1.2 实测表 + 长跑 59.6 tok/轮斜率。
- **方案**：
  - **A. 不动**。515 拍降级、987 场丢行——按「一场 ≈ 2.24 拍」是 894 拍无损。
    对一个剧情会话来说，「最旧的场次先掉细节」在 500 拍之后发生是**合理的产品行为**。
  - **B. softMax 提到 0.70**（archive 30690 → ~39000，覆盖约 655 拍）。
    成本：prompt token 上升，上游费用上升约 10–15%。
  - **C. 把 `recent` 的 0.40 份额让出一部分给 archive**。现在 `recent` 的 0.40
    **不参与求和**（它是「当前场该多大时强制封场」的规划上限）；
    真正的 archive 份额是 0.30。可以让 archive 0.34、scene 0.20。
- **我的倾向**：**先 A，不动**。理由是这条线目前**一次都没触发过**，
  在 1000 拍真实运行出现之前改它属于提前优化。如果确实要做千拍，我倾向 **C**
  （在做完 D1 之后 `recent` 的实际占用会变小，正好有空间可让）。
- **待拍板**：目标轮次是多少？（45 已做 / 200 / 1000）。这个数字决定 D2 与 D4 的优先级。

### D3【高收益，但需要动红线判断】四道静默硬顶改成「token 配额 + 显式降级」

- **问题**：断言 300 / 线索 40 / 关系 60 / 原声 400 行是 SQL `LIMIT`，
  在 token 预算之外先截断，且截断行为对模型不可见、对日志只有一行无人读的 meta。
- **证据**：§1.1 表 + 撞墙点推演。1000 拍时 6200 条断言只有最新 300 条可见，
  更早 5700 条对模型完全不存在。
- **方案**：
  - **A. 把四个 `LIMIT` 换成按 token 配额选，走与场次索引同一套降级。**
    具体：`assertions` 改成「单值谓词全渲染 + 多值按相关性取到 `scene` 配额为止」，
    而不是 `manyLimit: 10` 硬编码；`threads/relations` 同理按 token 选。
    成本：中（改 `context-engine.js` 取数 + `scene-sheet.js` 渲染 + 测试）。
  - **B. 保留 LIMIT，但把「被丢掉多少」变成模型可见的一行**：
    `场记单` 里加一句「另有 5700 条更早的事实未展开」。用一行文字换掉静默。
    成本：低。但违反 §1.2「先删后加」（这是往提示词里加话）。
  - **C. 什么都不改，只把 meta 接到报告里**（`longrun-report.mjs` 加判据），
    先量化真实长跑里掉了什么，再决定。
- **我的倾向**：**C → A 两步走**。先跑一局 200+ 拍的真实长跑（这是唯一还没有的数据），
  用 `meta.facts_many_dropped` 等字段看真实丢失曲线，再决定改哪一层。
  直接上 A 的风险是：`manyLimit: 10` 当初就是为了防「事实段膨胀吃掉场记单预算」，
  改成 token 驱动需要先把 `scene` 层 22506 tok 的内部分配理清楚（现在场记单内部
  是 need 段先占、可选段后占，事实段属于可选段）。
  **这里有一个真实的架构张力**：token 配额是软的（挤掉了还能降级），
  SQL LIMIT 是硬的（挤不掉，直接没有）。当初选硬顶大概是为了「保证不爆」，但代价是静默。
- **待拍板**：是否接受「先把 meta 接进报告、跑一局 200 拍再改」这个顺序？

### D4【必须先做】默认模式下模型无法回查历史原文

- **问题**：`recall_history` 与 `codex_lookup` 两个「模型主动取证」通道**只存在于分段模式**
  （`server/agents/orchestrator.js:200-211` 只在 `narrationMode === 'segmented'` 注入
  `recall` 回调；`server/agents/narrator.js` 完全没有任何 tools）。
  默认 `NARRATION_MODE=single`，所以 45 拍长跑里模型**没有任何手段回查**。
- **证据**：这是「布包被首次发现三次，三版互斥」「P1/P3/P4 三条语境级探针全编造」的
  结构性解释——不是模型不努力，是通道不存在。AGENTS §1.1 明确把这通道写成
  「允许的唯一例外」，但实际只在可选模式里接上了。
- **方案**：
  - **A. 单发模式也给 narrator 一个 `recall_history` 上下文预取**：
    由**代码**在装配时判断「本轮提到的人/物在库里有没有更早的记录」，有就带上——
    这就是「自动召回」，直接违反红线 1（不许按文本匹配自动塞设定/历史）。**否决**。
  - **B. 单发模式也开一次工具调用**（把 single 模式改成「一次工具往返 + 一次生成」）。
    成本：每拍多一次上游往返（约 +15–25% 延迟、+30% 成本）。
  - **C. 默认切到分段模式**（`NARRATION_MODE=segmented`）。功能上等价 B，
    但分段模式本身还有草稿/修订的额外开销，且默认关是有理由的。
  - **D. 只把 `recall_history` 做成模型可选的「一次性预取」**：装配前一轮，
    用当拍玩家行动做一次廉价检索判断，命中才给——这仍是「代码决定注入」，红线 1 否决。
- **我的倾向**：**B**。它的语义最干净：工具由模型自己发起（符合红线 1 的唯一例外），
  只是把「分段循环」这一层壳去掉。具体是 `runNarrator()` 支持一次
  `tool_calls` → 执行 → 二次调用的路径。代价是每拍多一次往返。
  **这条是我认为目前最值得做的单点改动**——它同时解释了「自造 canon」「断言编造」
  「台词复读」三类问题的一半。
- **待拍板**：接受每拍多一次往返（延迟 +15–25%、成本 +30%）吗？
  还是先在一局 200 拍里测「模型发起 recall 的频率」，用真实频率算成本再决定？

### D5【产品决策，不是 bug】线索只埋不收

- **问题**：`threads` 65 拍终态 60 行 / open 55 / resolved 5 = 10.8%，且 5 条里 3 条同一母题。
  没有积压压力机制。
- **证据**：eval §4.8。
- **方案**：
  - **A. 给史官加「回收」指令**：`sceneKeeper` 已经在读整场原文（PR-2 加的），
    让它顺带判「本场解决了哪条线索」。成本：低（一个字段 + 一条落库路径）。
  - **B. 在装配层做「线索过期」**：超过 N 拍没被提到的 open 线索降权/不渲染。
    成本：低，但会让「埋了 100 拍的伏笔」静默消失——反向伤害。
  - **C. 不改**。认为「只埋不收」是模型能力边界，由作者/玩家在提示词里管。
- **我的倾向**：**A**。理由：`sceneKeeper` 现在已经在读整场原文做生死交叉校正，
  加一个 `resolved_threads` 字段是同一个通道里的同类判断，不新增注入点（§1.2 合规）。
  而且要防止它乱收：可以让它只输出「候选」，由代码按「本场正文里确实提到了该线索」
  做确定性校验再落库（同 PR-2 的做法）。
- **待拍板**：同意让场记顺手做「线索回收判定」吗？还是希望「不收」是刻意保留的悬念？

### D6【产品决策】`uncertain` 的归宿

- **现状**：已改（P2，commit `613508b`）：按 kind 取数、`retirePatchesBeyond(keep:120)` 收敛。
  但**仍然没有消费方**——不进提示词、不进 threads、没有 agent 读。
- **方案**：
  - **A. 从 schema 删掉**（§1.2「先删后加」：没有消费方的产出就是纯成本）。
  - **B. 给校勘（continuity）读**：校勘本来就在找矛盾，`uncertain` 正是「模型自己举手
    说这里它不确定」的信号。让它作为校勘的输入，产出 `open` 矛盾供人复核。
  - **C. 进记忆面板的「待复核」列表**（已部分做到）。
- **我的倾向**：**B**。这是唯一让这笔产出产生价值的方式，而且不新增通道
  （校勘已经在读记忆表）。成本：低。
- **待拍板**：同意还是删？

### D8【前置：要不要现在做】`introduce` 出来实体的部分定义没有被任何层承载

- **问题**：§1.3 实测——`introduce` 写进 `world_state` 的字段里，有一部分**永远不再被渲染**：
  世界索引读模板快照（不含新实体），场记单的在场者渲染只读 `role/status/condition/mood/
  location/psyche.traits`，**`summary` 与 `identity.*`（外形/身份）不渲染**。
- **证据**（实测，已修正早期误判）：给一个只 `introduce` + 账本 `present` 的角色埋四个
  哨兵串，装配后 `role` ✔ 出现、`status` ✔ 出现、`psyche.traits` ✔ 出现、
  **`summary` ✘ 不出现**。另：只 introduce 不写 `present` → 上下文全文 0 次出现该名字。
  而 `sanitizeIntroduce()`（`server/agents/archivist.js:143-190`）的 person 分支
  **根本不收 `identity` 与 `voice`**（`detail` 也不收），所以外形/口吻连库都进不去。
- **可选方案**：
  - **A. 让场记单渲染在场者的 `summary`**（一行，加在 `renderCastLine` 的 state 之后）。
    成本：低（一个 `if`）。收益：「临时登场的人」不再只剩一句角色标签。
  - **B. 让 `sanitizeIntroduce()` 也收 `identity.appearance/station`**，走 A 的渲染面。
    成本：低，但要同步改 `state-paths` 的身份根禁令判断（appearance 不是身份根，可以放行）。
  - **C. 不改**。理由：临时登场的人本来就该「只有名字 + 状态 + 性格」，想让他有厚度
    就进断言；`summary` 属于「人物小传」，而场记单是当拍事实。
- **我的倾向**：**A（只加 summary 渲染），不动 sanitize 的收字段面**。
  理由：`summary` 已经在库里了（`introduce` 收了它），现在白白浪费；而外形/口吻属于
  「稳定形象锚点」，临时角色本来就不该有——那是卡里 `entities[]` 才该有的东西。
- **待拍板**：这条要不要现在做？还是认可「临时角色不渲染摘要」是刻意取舍？
